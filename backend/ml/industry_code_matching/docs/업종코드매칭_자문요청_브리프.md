## 0. 한 줄 요약

한국 국세청 6자리 "업종코드"(총 1,612개)를 사업 설명 텍스트로부터 자동 매칭하는 RAG 시스템을 만들었는데,
**(1) 정확도가 어려운 테스트셋 기준 Top-1 57.5%에서 안 올라가고,
(2) 개선을 시도해도 그게 효과가 있는지 측정할 신뢰할 만한 방법이 없다.**
무엇이 근본 문제인지, 접근 방향이 맞는지 조언을 구합니다.

## 1. 문제 도메인

- **목표:** 소상공인/예비창업자가 자기 사업을 자연어로 설명 → 국세청 6자리 업종코드 1개(+대안)를 자동 부여.
- **분류 체계:** 국세청 업종코드 1,612개. 한국표준산업분류(KSIC) 11차와 연계됨. 세세분류 수준이라 매우 잘게 쪼개져 있음.
- **어려운 점:**
  - 코드가 재료·용도 중심으로 세분화됨 (예: "곡물 제분업", "비 및 솔 제조업", "전시용 모형 제조업").
  - **공식 분류가 직관에 반하는 경우가 많음.** 예:
    - "밀가루·콩가루 제조" → 정답 `곡물 제분업`
    - "페인트용 롤러 제조" → 정답 `비 및 솔 제조업`
    - "공기주입식(에어) 매트리스 제조" → 정답 `천막, 텐트 및 유사 제품 제조`
    - "새 깃털로 장식품 제조" → 정답 `전시용 모형 제조업`
  - 활동 설명 단어와 정답 코드명이 **한 단어도 안 겹치는** 케이스가 흔함.
- **실무 제약:** 실제 사용자가 부여한 라벨 데이터(정답)가 **없음.** 통계청 KSIC 11차 해설서(공식 문서)로 부트스트랩 중.

## 2. 현재 시스템 아키텍처 (RAG)

입력(사업설명 3항목: 문제/솔루션/시드문장) → 아래 6단계:

```
① LLM이 텍스트를 구조화
   - canonical_activity : 분류표 어투로 정규화한 활동명 ("커피 가공업")
   - business_role      : 18종 enum (제조·가공 / 도매 / 소매 / 음식·주점 / 건설·시공 ...)
   - search_keywords    : 핵심 제품/서비스 명사 2~6개
   - product_service    : 제품/서비스 서술

② 멀티쿼리 벡터 검색 (ChromaDB, text-embedding-3-small)
   - 쿼리 3가지 표현으로 각각 검색 후 병합:
     (a) canonical_activity 단독
     (b) canonical + role + product + keywords
     (c) product + keywords  (canonical이 틀렸을 때 보완)
   - VECTOR_PER_QUERY = 40

③ 키워드 검색 (동의어 확장 포함) → 벡터 결과와 하이브리드 병합
   - 후보 pool 상위 ~20개(RERANK_TOP_N=20) 확보

④ LLM 재판정 (rerank)
   - business_role과 상충하는 후보를 먼저 제외
     (직접 제조인데 도매 후보 / 매장조리인데 제조 후보 / 고객의 업종에 해당하는 후보 등)
   - 남은 후보 중 세세분류명·세부설명이 가장 직접 일치하는 것 선택 + 이유 생성
   - LLM 자기 신뢰도(high/mid/low) 부여

⑤ 신뢰도 산정 = LLM 자기판단 + 검색신호 가드
   - 재판정이 후보 4위 이하 선택 → 하향
   - 벡터·키워드 한쪽에서만 잡힘 → 하향
   - 1·2위 cosine 차 < 0.06 이고 1위 아님 → 하향

⑥ 출력: 대표코드 + 대안 2·3위 + 신뢰도 + 역할
```

- LLM: `gpt-5-mini` (temperature 기본값, 비결정적)
- 임베딩: `text-embedding-3-small`
- 검색 문서(색인 대상): 업종코드 1개 = 여러 짧은 문서로 분할 (영국 ONS ClassifAI 방식 벤치마킹)
  - `name` : 세세분류명
  - `hier` : 대>중>소>세분류 계층 경로
  - `ksic` : 연계 KSIC 분류명
  - `desc` : 세부설명 (있을 때만)
  - 총 3,948개 문서 / 1,612개 코드

## 4. 현재 성능 (실측)

### 4-1. gold_set_v2 (240건) — "어려운" 테스트셋

- 구성: 통계청 KSIC 11차 해설서의 `<예시>` 200건 + `<제외>` 40건을,
  LLM(gpt-4o-mini)이 PSST 스타일 사업설명 문장으로 풀어써서 만듦. 라벨은 해설서 근거.

| 방식 | Top-1 | Top-3 | Top-5 |
|---|---|---|---|
| A. 원문 임베딩 (LLM 없음) | 24.6% | 38.3% | 43.3% |
| B. LLM 구조화 + 멀티쿼리 임베딩 (후보 pool) | 40.4% | 53.3% | 60.0% |
| **C. B + LLM 재판정 (최종)** | **57.5%** | — | — |
| 정답이 후보 pool TOP-20 안에 포함 | 70.4% | | |
| 정답이 후보 pool 전체에 포함 | 80.4% | | |

**오답 102건 분해:**
- **검색 실패 47건**: 정답이 후보 목록에 아예 없음 (retrieval recall 문제)
  - 제조·가공 역할이 29/47
  - 정답이 "기타/그 외" 계열 제네릭 코드가 18/47
  - 42/47은 원문 임베딩(A)으로도 못 찾음 → 코드 문서 자체에 연결고리 부재
- **재판정 실패 55건**: 후보엔 있으나 LLM이 오답 선택
  - 다수가 **소매/도매 ↔ 제조·가공 역할 혼동** (예: 안경 소매 → 안경 제조업 선택)
  - 절반가량은 정답이 pool 20위권 밖 (사실상 검색 문제 연장)

### 4-2. gold_set_v1 (42건) — 손으로 만든 작은 셋 (해설서와 무관)

| 인덱스 버전 | A Top-1 | B Top-1 | **C Top-1** | pool 포함 |
|---|---|---|---|---|
| 베이스라인 (name/hier/ksic/desc만) | 38.1% | 64.3% | **95.2%** | 97.6% |
| + 해설서 예시 전체 색인 (8,027 문서 추가) | 54.8% | 64.3% | **83.3%** | 95.2% |
| + 해설서 예시 선별 색인 (536 문서, 70개 코드) | 35.7% | 57.1% | **88.1%** | 95.2% |

## 5. 시도한 개선과 결과

**가설:** 검색 실패의 근본원인은 검색 문서에 "이 활동 = 이 코드"라는 구체적 연결고리가 없어서다.
통계청 해설서 `<예시>` 활동 문구(예: "볶은 커피 생산", "규산질 토 채굴")를 이미 5,411개 추출해 뒀으니, 이걸 검색 문서로 색인하면 반직관 케이스가 잡힐 것이다.

**시도 1 — 예시 5,411개 전체를 검색 문서로 색인:**
- 결과: 원문 임베딩(A)은 38→55%로 상승. **하지만 최종(C)은 gold_v1에서 95→83%로 하락.**
- 원인 분석:
  - 예시 문구의 40%가 제조업. 문구가 매우 구체적("황산비소광 채굴", "펄프 가공기 제조").
  - "안경 판매" 같은 애매한 쿼리가 "안경테 제조", "렌즈 가공" 예시 문서를 끌어옴 (어휘 유사).
  - 재판정 LLM의 역할 구분력이 이 함정을 못 걸러냄 → 소매 케이스가 제조로 감.
  - 일부 흔한 소매코드(전자상거래 소매업)가 예시 홍수에 밀려 후보 pool에서 탈락.

**시도 2 — 실제 검색 실패했던 70개 코드에만 예시 선별 색인 (536 문서):**
- 결과: C가 gold_v1에서 88.1%. 전체 색인(83%)보단 낫지만 **베이스라인(95%)은 여전히 못 넘음.**
- 문제:
  - gold_v1에는 그 70개 타깃 코드가 거의 없어서 개선 효과가 측정될 데가 없음.
  - `gpt-5-mini` 비결정성 때문에 42건에서 **run마다 ±7%p 흔들림** (동일 케이스가 무관한 변경에도 O↔X 뒤집힘).

## 6. 지금 막힌 핵심 (2개 층)

### 층 1 — 시스템 실패 유형 (근거 있음)
- retrieval recall이 낮다 (240건 중 47건은 정답이 후보에 없음).
- 재판정이 소매/도매를 제조·가공으로 혼동한다 (55건).

### 층 2 — 측정 불가 (진짜 벽)
- **해설서와 무관한 테스트셋이 42건뿐.** 통계적으로 부족(정확도 구간 60~90%에서 ±5% 신뢰구간엔 100~350건 필요).
- **LLM이 비결정적.** 1회 측정값이 불안정. 42건 × 비결정 = ±7%p 노이즈.
- **240건 테스트셋은 순환.** 그 문장들이 해설서 예시를 풀어써서 만든 것이라, 해설서 예시를 검색에 넣고 240건으로 채점하면 "답을 미리 본 시험"이 됨.
- 결과: **5%p짜리 개선을 만들어도 감지할 수단이 없음.**

### 순환 구조 다이어그램
```
KSIC 11차 해설서 <예시> 5,411건
        │
        ├──(`parse_ksic_haeseol.py` 파싱)──> 검색 인덱스에 넣고 싶은 데이터
        │
        └──(`build_gold_from_haeseol.py` LLM 풀어쓰기)──> gold_set_v2 240건 (테스트 문제지)

  → 같은 소스에서 나온 둘로 "색인"과 "채점"을 하면 성능이 부풀려짐
  → 순환을 피하려면 42건짜리 gold_v1만 남는데, 너무 작고 노이즈가 큼
```

## 8. 자문 구하고 싶은 질문

1. **접근 방향 자체가 맞나?** RAG(임베딩 검색 + LLM 재판정)가 1,612개 세세분류 분류에 적합한가, 아니면
   계층적 분류(대→중→소→세 단계별 좁히기), 파인튜닝 분류기, 또는 다른 인덱스 구조로 가야 하나?

2. **순환을 어떻게 깨나?** 실제 라벨 데이터 없이 신뢰할 수 있는 평가셋을 어떻게 만드나?
   - 후보: (a) 통계청/국세청 분류 질의응답·민원 사례, (b) 다른 LLM이 코드명+정의문만 보고(해설서 예시는 안 보고) 사업설명 생성, (c) 사람이 100건 작성+해설서 참조 라벨링

3. **예시 색인이 원문 검색(A)은 올리는데 최종(C)은 내리는 이유?**
   예시 신호를 재판정 LLM을 헷갈리지 않게 넣는 방법? (doc_type별 검색 분리? 예시 가중치 조정? 예시는 재판정 근거로만 쓰고 검색엔 안 넣기?)

4. **1,612개 세세분류에서 Top-1 57.5%가 실제로 합리적인 수준인가,** 아니면 뭔가 근본적으로 잘못됐다는 신호인가?
   (참고: BEACON, ONS ClassifAI 등이 유사 과제에서 보고하는 정확도 수준을 아신다면)

5. **BEACON식 검색/검증 분리를 더 밀어붙여야 하나?** 지금도 분리돼 있지만 재판정이 여전히 약함.

6. **재판정의 소매/도매 ↔ 제조·가공 역할 혼동** — 프롬프트 개선, 입력 구조화 개선, 아니면
   역할을 먼저 확정하는 별도 분류기를 앞단에 두는 게 맞나?

7. **LLM 비결정성 대응** — 케이스당 k회 반복 + 다수결/평균이 표준인 건 알지만, 비용·시간이 큼.
   temperature=0으로 충분한가? 더 작은 평가셋을 여러 번 vs 큰 평가셋 1번 중 무엇이 나은가?

# 업종코드 자동매칭 — 기능 전체 브리프 (2026-09-09 기준)

> **이 문서의 용도:** 이 기능을 이어받거나, 다른 AI·전문가에게 검토·조언을 구할 때
> 그대로 붙여넣는 자립형 문서. 배경지식 없는 사람이 읽어도 이해되도록 작성.
> 프로젝트: 물꼬(Mulkko) 3차 프로젝트, 업종코드 파트.

## 0. 한 줄 요약

사용자가 사업을 자연어로 설명하면(질문 3개 답변) → 국세청 **6자리 업종코드**(1,612개 중 1개)를
자동으로 도출하는 RAG 시스템. **2026-09-09 기준 최종 정확도 Top-1 67.1%**(어려운 테스트셋 240건),
정답이 후보에 포함되는 비율 97.5%. 담당 범위(사업설명→업종코드)는 완성, 백엔드 연동 단계.

## 1. 기능 개요

### 목표
소상공인·예비창업자가 자기 사업을 글로 설명 → 6자리 업종코드 자동 부여.
이 코드는 이후 지원사업 자격 판정·상권 통계·지역 매칭의 입력이 됨.

### 분류 체계
- 국세청 업종코드 1,612개 (한국표준산업분류 KSIC 11차와 연계, 세세분류 수준)
- **공식 분류가 직관에 반하는 경우가 많음:**
  - "밀가루·콩가루 제조" → 정답 `곡물 제분업`
  - "페인트용 롤러 제조" → 정답 `비 및 솔 제조업`
  - "에어 매트리스 제조" → 정답 `천막, 텐트 및 유사 제품 제조`
  - "새 깃털 장식품 제조" → 정답 `전시용 모형 제조업`
- 활동 설명 단어와 정답 코드명이 한 단어도 안 겹치는 케이스가 흔함

### 제약
- 실제 사용자가 부여한 정답(라벨) 데이터가 **없음**. 통계청 KSIC 11차 해설서(공식 문서)로 부트스트랩.

### 담당 범위
"사업 아이디어 → 업종코드"까지. 이후 지역·지원사업·상권 매칭, 창업유형 분류(기술창업형 등)는 별도 파트.

## 2. 아키텍처 (RAG, 2026-09-09 현재 버전)

입력: PSST 자유 텍스트 3개 (seed 20~120자 / problem 20~250자 / solution 20~300자)

```
① GPT-5-mini 구조화 : 실제 수익활동 1~3개 추출 (업종코드는 생성 안 함)
   - canonical_activity : 분류표 어투로 정규화한 활동명 ("커피 가공업")
   - business_role      : 18종 enum 중 하나 (제조·가공 / 도매 / 소매 / 음식·주점 /
                          중개·플랫폼·정보제공 / 건설·시공 / 정보서비스·SW개발 ...)
   - search_keywords, product_service, priority(primary 1개)

   ※ 역할 판단 규칙(프롬프트): 직접 만들면 제조 / 떼다 팔면 도소매 / 연결 수수료면 중개 /
     매장 조리면 음식점 / 플랫폼·AI는 그 자체가 상품 아니면 역할 아님.
   ※ 카브아웃: 판매 전 손질·선별·소분·재포장은 제조 아님(도소매) / 안경원은 소매.

② 임베딩 검색 (text-embedding-3-small, ChromaDB) — 2개 채널 분리
   - BASE 채널   : 공식정보 문서(업종명/계층/KSIC/정의) → 상위 25개 반드시 유지
   - EXAMPLE 채널: 해설서 <예시>/<제외> 활동 문구      → 상위 12개를 '추가만'(BASE를 못 밀어냄)
   - 쿼리 3가지 표현으로 multi-query 후 코드별 최고순위로 병합

③ 키워드 검색(동의어 확장) 보완 → 통합 후보 Pool
   - 역할 상충 후보(role vs 대분류)는 검색순위 +12칸 뒤로, 역할 부합은 -6칸 앞으로 (완전배제 아님)

④ GPT-5-mini 재판정 (후보 상위 20개)
   - 판정 순서: 1)역할 적합성  2)제품/서비스 직접일치  3)해설서 포함 예시  4)해설서 <제외> 위반  5)KSIC  6)계층
   - 후보별로 "역할 적합성: 부합/중립/상충" + "이 코드가 아닌 활동(해설서 제외)" 노트 제공
   - 후보 목록 밖 코드 생성 금지
   - 역할 라벨이 명백히 잘못됐으면 활동 설명 우선(구조화 오판 복구)

⑤ 신뢰도 산정 = 재판정 LLM 자기판단(high/mid/low) + 검색신호 가드로 하향만
   - 재판정이 후보 4위 이하 선택 → 하향
   - 벡터·키워드 중 한쪽에서만 잡힘 → 하향
   - 1·2위 유사도차 < 0.06 이고 1위 아님 → 하향
   - (6위+ AND 한쪽만) → low 확정

⑥ 출력: 대표 업종 1개 + 부가 업종 0~2개 + 각각 신뢰도·대안 2·3위
```

- LLM: `gpt-5-mini` (temperature 기본값 = 비결정적)
- 임베딩: `text-embedding-3-small`
- 벡터 DB: 14,627 문서 / 1,612 코드. 문서유형 name/hier/ksic/desc/example/xref
- 해설서 `<제외>` 노트: 904개 코드에 매핑

## 4. 2026-09-09 개선 내역 (아키텍처 유지, 최소 수정)

### 배경 — 개선 전 문제 2가지 (gold_v2 240건 실측)
1. **검색이 정답을 후보에 못 올림** — 240건 중 47건 (제조·가공 29건 집중, "기타/그외" 코드 18건)
2. **역할 혼동** — 소매인데 제조업, 도매인데 가공업으로 재판정이 오선택 (55건)

### 개선 1 — 역할(role) 확정 강화
- 구조화 프롬프트에 `[역할 확정 규칙]` + `[제조로 착각하기 쉬운 도매·소매·서비스]` 카브아웃.
- **핵심 발견:** 실패 대부분이 재판정이 아니라 **구조화 단계**. gpt-5-mini가 "손질·선별·조제·조립"
  단어에 `제조·가공`을 과잉 발동 (활어 도매→수산가공, 안경원→안경제조).

### 개선 2 — Role-aware 후보 필터
- 후보 대분류가 역할과 명백히 상충하면 검색순위 +12칸 뒤로, 부합하면 -6칸 앞으로.
- **완전 배제 아님** — 구조화가 역할 오판해도 상충 후보가 재판정 창에 남아 LLM이 되돌릴 수 있음.

### 개선 3 — 검색 채널 분리
- BASE(공식정보) 25개는 반드시 유지, EXAMPLE(해설서 예시·제외) 12개는 추가만.
- 이전 시도(해설서 예시 5,411개를 한 pool에 섞음)는 제조업 예시가 검색을 오염시켜
  gold_v1 정확도를 95→83%로 떨어뜨렸음. 채널 분리로 해결.

### 개선 4 — 해설서 `<제외>` 규칙 반영
- `25번`: `xref` 문서유형 신설. "이 활동은 A가 아니라 B로 간다"의 B 코드에 그 활동을 색인 (2,859개).
- `23번`: `load_exclusion_notes()`. 재판정 프롬프트가 후보별 제외 규칙을 근거로 받음.

### 결과 (검증 완료)

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| gold_v2 240건 C Top-1 | 57.5% | **67.1%** (+9.6%p) |
| gold_v2 정답이 후보에 포함 | 80.4% | **97.5%** (+17%p) |
| gold_v2 검색 실패 건수 | 47 | **6** |
| gold_v2 high 신뢰도 실측 정확도 | 72% | **83.5%** |
| gold_v1 42건 C Top-1 | 95.2% | 92.9% (LLM 비결정성 범위 내 동급) |
| 대표 + 대안 3개 안에 정답 | — | 약 74% |

케이스 이동: 개선 32건 / 악화 9건.

## 7. 백엔드 통합

### 진입점
```python
from industry_matcher import match_business_code, warm_up, health

warm_up()          # 서버 기동 시 1회 (모델·DB·해설서 노트 예열)
health()           # 정상값: chroma_doc_count 14627, reference_rows 1612

r = match_business_code(seed, problem_to_solve, solution_approach, region="")
rep = r["representative_business"]
#   rep["business_code"]   → 6자리 코드
#   rep["business_name"]   → 업종명
#   rep["confidence"]      → high/mid/low (UI 분기)
#   rep["alternatives"]    → 대안 후보 (최대 3, "다른 업종 같아요"용)
#   rep["user_selected_code"], rep["changed_by_user"] → 백엔드가 채움 (사용자 선택 로그)
# r["additional_businesses"] → 부가 업종 0~2개 (구조 동일)
```

## 8.5 논문·해외 공식통계 기관 근거 (2026-09-09 조사)

이 기능의 설계는 즉흥이 아니라 **공식통계의 "산업·직업 자동코딩(automated industry/occupation coding)"**
이라는 확립된 연구 분야의 표준 방식을 따른 것이다.

### 우리 설계 ↔ 근거 매핑

| 우리가 한 것 | 근거 | 비고 |
|---|---|---|
| write-in 텍스트 → 순위 매긴 6자리 코드 후보 → 사용자가 선택 | 미국 Census **BEACON** (*Business Establishment Automated Classification Of NAICS*, 2022 경제센서스) | **설계가 사실상 동일** |
| 검색(후보 생성)과 재판정(검증)을 분리 | BEACON, 영국 ONS SIC/SOC 코딩 | |
| high/mid/low 신뢰도로 자동수용 vs 사용자확인 분기 | Schierholz & Schonlau (2021), *"Machine Learning for Occupation Coding—A Comparison Study"*, JSSAM — 하이브리드(ML+규칙)+임계값이 정확도 98~100% 달성 | 우리 high 버킷 83.5%는 아직 하이브리드 수준엔 못 미침 |
| 분류 체계를 임베딩 + RAG로 검색 | arXiv **2409.11524** *"Unlocking NACE Classification Embeddings with OpenAI"* (2024) — LLM+RAG로 회사 설명을 1,800개+ 산업분류로 | 가장 가까운 최신 사례 |
| 키워드/동의어 매칭 보완 | 영국 ONS — "text→code 매칭 규칙 knowledge base" + fuzzy matching 후 나머지만 ML | 우리 SYNONYMS 딕셔너리가 축소판 |
| 사용자 선택을 로그로 축적해 재학습 | ONS(지속 갱신 knowledge base), 캐나다 ACA-NOC(반복 개발형) | 브리프 §8-4와 동일 |

### 정확도 벤치마크 맥락 (직업 코딩 문헌)

| 방식 | 자동처리율 | 정확도 |
|---|---|---|
| 사전(dictionary) 기반 | 43% | 94% |
| 순수 ML | 100% | 최대 **80%** |
| 하이브리드(ML + 규칙 + 임계값) | 73~80% | 98~100% |
| 한국 통계청 KoBERT (인구주택총조사 실데이터 학습) | — | 산업 95.7% / 직업 91.5% |

→ 우리: 자동처리율 100%(항상 반환) + Top-1 **67%**. 순수 ML 자동화 범위 안.
통계청 95%는 **센서스 실응답 = 대규모 정답 데이터로 학습**한 결과 — 우리에게 없는 자산(브리프 §6 한계와 대응).

### 논문 기반 개선 로드맵 (우선순위, 크레딧 필요 항목 표시)

| # | 개선 | 논문 근거 | 크레딧 | 상태 |
|---|---|---|---|---|
| A | 대안 후보를 3→5개로, mid/low면 더 넓게 | BEACON(순위 후보 리스트) | 불필요 | ✅ 반영(`pick_alternatives` 기본 n=5) |
| B | `RERANK_TOP_N` 20→28 | 재판정 실패 42/73이 pool 15위+ | 필요(~$3) | ⬜ 미검증 |
| C | 한국어 특화 임베딩 모델 검토 (KURE, bge-m3, KoSimCSE 등) | 통계청 KoBERT — 한국어 인코더가 검색 품질 좌우 | 필요(재색인+재평가) | ⬜ 조사만 |
| D | 하이브리드 강화 — 키워드/규칙 knowledge base를 명시적 1차 패스로 | ONS 방식 | 일부 필요 | ⬜ |
| E | 앙상블 — 원문검색(A) + 구조화검색(B) 결과를 투표로 결합 | Schierholz·Schonlau(방법 결합이 유리) | 필요(튜닝) | ⬜ |
| F | 사용자 선택 로그 → 비순환 정답셋 → 신뢰도 임계값 데이터 재설정 | ONS, ACA-NOC, Schierholz | 서비스 운영 | ⬜ |

**중요:** B~E는 **테스트 없이는 개악 위험**이 있다 (예: 2026-09-08 예시 색인 시도가 검증 없이 gold_v1을 95→83%로 떨어뜨림). 크레딧 복구 후 gold_v2로 A/B 비교하며 하나씩 반영할 것.

## 9. 판단이 필요한 열린 질문 (검토·조언용)

1. **RAG 접근이 맞나?** 1,612개 세세분류에서 Top-1 67%. 계층적 분류(대→중→소→세 단계별 좁히기),
   파인튜닝 분류기로 가야 하나, 아니면 이 방향으로 튜닝을 계속하나?
2. **테스트셋 순환을 어떻게 깨나?** 실제 라벨 없이 신뢰할 평가셋을 어떻게 만드나?
   (통계청 분류 질의응답 / 다른 LLM이 코드명+정의만 보고 생성 / 사람이 해설서 참조 라벨링)
3. **제조·가공 반직관 케이스** — 통계청 특유 분류(침구→임산물 채취 등). 해설서 예시 색인으로도
   재판정이 못 넘음. 별도 처리가 필요한가?
4. **1,612개 분류에서 67%가 합리적 수준인가?** 유사 과제(미국 Census BEACON, 영국 ONS ClassifAI)의
   보고 정확도와 비교하면?
5. **비용/속도** — 요청당 gpt-5-mini 3회 호출, 8~20초. 재판정 창 축소·모델 교체·캐싱 중 무엇을 먼저?

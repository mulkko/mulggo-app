물꼬 · 3차 프로젝트 개발 현황

사업 아이디어를 6자리 업종코드로 매칭하기

사용자가 PSST로 입력한 사업 아이디어를 분석해 국세청 업종분류표의 6자리 업종코드를 자동으로 찾아주는 기능. 검색 품질이 왜 낮았고, 무엇을 고쳤는지 정리한다.

대상 데이터 업종코드-표준산업분류 연계표 (1,612개 코드) 작업 폴더 business_matching/ 기준일 2026-09-08
01 — 개요

이 기능이 하는 일

사용자는 PSST 슬롯에 사업 아이디어(슬롯 0), 문제·기회(슬롯 2), 사업화 방식(슬롯 5)을 입력한다. 시스템은 이 세 가지만 사용해 실제로 돈을 버는 사업활동을 1~3개로 정리하고, 각 활동에 가장 잘 맞는 6자리 업종코드를 찾는다. 지역(슬롯 14)은 업종 판정에 넣지 않고, 업종코드가 확정된 뒤 지원사업·상권·시장분석에만 쓴다.

최종 출력은 KSIC 코드가 아니라 ‘업종코드-표준산업분류 연계표.csv’의 6자리 업종코드다. 예: 154901 커피 가공업, 552303 커피 전문점. 앞자리 0이 날아가면 안 되므로 항상 문자열로 다룬다.
02 — 진단

“코사인 유사도가 낮다”를 실제로 재본 결과

같은 커피 사례를 여러 방식으로 임베딩 검색해 봤다. 정답은 154901(커피 가공업)과 552303(커피 전문점)이다.

검색 쿼리1위 결과정답 순위해석
커피 원두 가공 및 제조 154901 커피 가공업 1 깔끔한 분류표 용어면 잘 맞는다
커피 원두 로스팅 및 판매 512273 커피 및 차류 도매업 2 “판매”가 도매 쪽으로 끌어당김
카페에서 커피 음료 제조 및 판매 154901 커피 가공업 3 “제조”가 제조업 쪽으로 끌어당김
커피 전문점 운영 552303 커피 전문점 1 역할이 분명하면 정확하다

임베딩 모델(text-embedding-3-small)로 짧은 한국어 문구를 비교하면 코사인 절댓값이 원래 0.3~0.5로 낮게 나온다. 이건 정상이고, 임베딩 자체는 문제가 없다. 진짜 문제는 두 가지였다 — 쿼리 문구가 사업자의 역할을 흐리면 엉뚱한 업종으로 끌려가는 것, 그리고 검색 문서가 코드번호·라벨로 지저분한 것(09 참고).

03 — 원인

검색이 흔들린 3가지 이유

CAUSE 1

오염된 표현

LLM이 만든 검색어에 “판매·온라인·앱·제조” 같은 단어가 섞이면 그쪽 업종으로 벡터가 쏠린다.

CAUSE 2

역할 구분 없음

제조·도매·소매·음식점 중 무엇인지 명시하지 않으면, 재판정 단계에서도 후보를 걸러낼 기준이 없다.

CAUSE 3

단일 표현 검색

한 가지 문구로만 검색하면, 그 문구가 조금만 어긋나도 정답이 후보군 밖으로 밀려난다.

핵심은 “정답이 후보군 안에 들어오는가”(retrieval)다. 후보에 정답이 없으면 아무리 좋은 LLM도 정답을 고를 수 없다.

신뢰도 = 재판정 LLM의 자기판단(high/mid/low) + 검색 신호 가드(후보 6위↓ 선택, 한쪽 검색만 잡힘 → 한 단계 하향). 가드 덕에 high 버킷은 42건에서 오답 0건. 코사인 마진 등 숫자는 저장만 하고 임계값은 정답셋 확대 후 결정(인수인계서 24절).

이 결과가 말해주는 것

  • 3단계가 각각 기여한다. 원문만(A) 38% → LLM 활동 구조화(B) 64% → 재판정(C) 95%. "검색 + 검증 분리"(BEACON/ONS) 구조의 효과를 국내 6자리 코드에서 정량 입증.
  • 재판정이 가장 큰 폭. B에서 정답이 pool에 있어도(98%) 1위는 64%뿐인데, 역할 기준 재판정으로 95%.
  • 신뢰도가 잘 맞는다. "high"라고 한 35건은 실제로 전부 정답. 사용자에게 확신도를 보여줄 근거가 생김.
  • 남은 오답 2건은 검색 약함. "화초"·"도배장판" 같은 특정 용어에서 임베딩이 정답 문서를 못 잡음. 품목 동의어를 늘리거나 정답셋을 키워 재보정하면 개선 여지.
  • n=42는 방향 확인엔 충분하나 소수점까지 믿을 규모는 아니다. 100건대가 이상적.

08 — 상태

업종코드 매칭 기능: 완료

담당 범위(사업 아이디어 → 대표 업종 1 + 부가 0~2)는 완료. C Top1 95.2%, 신뢰도 high 버킷 정확도 100%, 복수활동 분해 동작 확인.

  1. 파이프라인 구현 (활동 구조화 → 멀티쿼리 검색 → 재판정 → 대표+부가)
  2. ONS 방식 다중 검색문서 DB 재구축
  3. 정답셋 42건 + 3단계 튜닝 (재판정 창 20, 프롬프트 규칙, 품목 동의어)
  4. 후보 alternatives + ai_predicted_code/score + user_selected_code/changed_by_user 출력
  5. 신뢰도 = LLM 자기판단 + 검색 신호 가드, 42건에서 검증 (high 100%)

  • 남은 오답 2건(꽃집·도배) — 품목 동의어 보강 또는 임베딩 문서 개선

09 — 벤치마킹

해외 사례 대조와 진행 로그

미국 Census BEACON과 영국 ONS ClassifAI는 공통적으로 자유 텍스트를 곧바로 코드 하나로 확정하지 않고 후보 검색과 검증 단계를 분리한다. 우리는 여기에 PSST 질문형 입력, 복수 수익활동 분해, 국내 6자리 업종코드 매칭, 지원사업·시장분석 연결을 더했다.

벤치마킹 포인트우리 시스템 반영상태
BEACON — 즉시 확정 X, Top-K 후보 검색·랭킹활동 → 벡터·키워드 후보 pool → 재판정반영
ONS ClassifAI — 분류 1개 = 검색문서 여러 개업종코드 1개 → name·hier·ksic·desc 문서 (1,612 → 3,948)반영 (2단계)
Retrieve → Verify — 전체 코드공간 자유생성 금지LLM은 활동 구조화·후보 안 재판정만. 코드 직접 생성 불가반영
사용자 확인·보정 — 다른 후보 선택 가능alternatives + ai_predicted_code/score + user_selected_code/changed_by_user 자리출력 반영
자체 차별화 — PSST 입력 / 복수 수익활동 분해PSST 0+2+5 소비 / 1~3활동 분해 → 대표 1 + 부가 0~2반영

담당 범위 명시: 이 파트는 "사업 아이디어 → 6자리 업종코드(대표 1 + 부가 0~2)"까지다. 업종코드 확정 이후의 지역 결합·지원사업·상권·시장분석은 별도 파트이며, 슬롯필링 인터페이스(입력 3개 텍스트)는 제안서 그대로 유지된다.

진행 로그

  • 1단계 — 23_v3 결과에 활동별 후보 2·3위(alternatives), ai_predicted_code / ai_predicted_score / user_selected_code / changed_by_user 자리 추가. 재판정 창 10 → 15.
  • 2단계 — 25·26 신규. "업종코드 1개 = 거대한 문서 1개"(코드번호·라벨이 벡터를 희석)를 버리고 짧고 깨끗한 문서 여러 개로 재구축(1,612 → 3,948). "커피 원두 가공" → 154901 코사인 0.42 → 0.67.
  • 3단계 — 오답 분석 후 저위험 수정: 재판정 창 15 → 20, 재판정 프롬프트에 "매장 조리=음식점 / 재고 매입·마진=도매(≠중개) / 인터넷 소매=전자상거래" 규칙, 키워드 검색 품목 동의어(꽃↔화초, 수산물↔활어·횟감 등). C Top1 85.7% → 95.2% (42건 재평가).
  • 3단계+ — 활동 구조화 프롬프트에 "직접 로스팅·제조·재배하면 도매·온라인으로 팔아도 canonical은 제조업·가공업·재배업" 규칙 추가(판매 채널을 업종으로 착각 방지). 실패 케이스(로스터가 "도매 공급" 강조 시 커피 도매업으로 오분류)를 개별 검증해 해결 확인. 전체 재평가는 API 지연으로 미완료 — 규칙이 기존 규칙의 명확화라 회귀 위험 낮음.
  • 신뢰도 — 재판정 LLM 자기판단에 검색 신호 가드를 얹어 42건에서 high 버킷 정확도 100% 확인.
부록

코사인 유사도를 어떻게 해석하는가

코사인 값은 정답 확률이 아니다. cosine = 0.55가 “정답 확률 55%”라는 뜻이 아니라, 임베딩 공간에서 두 벡터의 방향이 얼마나 가까운지를 나타내는 상대적 유사도다. 정답인데 0.4대가 나올 수도 있고, 0.80과 0.79처럼 붙어 있으면 후보 간 차이가 거의 없어 애매할 수 있다.

그래서 이 시스템은 코사인을 최종 신뢰도로 쓰지 않고 후보 검색(retrieval) 지표로만 쓴다. 실제 성능은 정답셋으로 따로 검증한다.

근거 문헌

  • Sentence-BERT (Reimers & Gurevych, 2019) — 문장을 임베딩 벡터로 만들어 코사인 유사도로 의미적 근접도를 비교.
  • Correlation Coefficients and Semantic Textual Similarity (Zhelezniak et al., 2019) — 코사인 유사도는 널리 쓰이지만 절댓값을 곧바로 정답 확률로 해석하면 안 됨.
  • Vector Space Model 계열 — 문서와 질의를 벡터 공간에서 비교하는 정보검색의 기본 배경.

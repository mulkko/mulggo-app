01이 기능이 하는 일

소상공인·예비창업자가 사업 아이디어를 글로 설명한다(질문 3개 답변). 시스템이 그 텍스트에서 실제 수익활동을 뽑아내고, 그에 맞는 국세청 6자리 업종코드를 대표 1개 + 부가 0~2개로 신뢰도와 함께 반환한다.

입력 슬롯내용길이
seed사업 아이디어 시드 문장20–120자
problem풀려는 문제 / 기회20–250자
solution사업화 방식20–300자
region지역 — 업종 판정에 안 씀, 통과만제한 없음
담당 범위

"사업 아이디어 → 업종코드"까지. 그 뒤의 지역 결합 / 지원사업 자격 판정 / 상권·시장 분석 / 창업유형 분류는 전부 별도 파트다. 이 코드는 그 파트들의 입력이 된다.

02왜 어려운가

  • 분류가 1,612개로 잘다. 세세분류 수준이라 재료·용도 중심으로 쪼개져 있음.
  • 공식 분류가 직관에 반한다. "밀가루 제조" → 정답 곡물 제분업 / "에어 매트리스 제조" → 정답 천막·텐트 및 유사 제품 제조 / "페인트용 롤러 제조" → 정답 비 및 솔 제조업.
  • 활동 설명 단어와 정답 코드명이 한 단어도 안 겹치는 케이스가 흔하다.
  • 실제 사용자 정답(라벨) 데이터가 0건. 통계청 KSIC 11차 해설서(공식 문서)로 부트스트랩 중.

이 기능의 설계는 즉흥이 아니라 공식통계의 "산업 자동코딩(automated industry coding)" 이라는 확립된 분야를 따른 것이다. 미국 Census BEACON(경제센서스 자가분류 도구, 검색→후보 리스트→사용자 선택), 영국 ONS ClassifAI(코드 1개 = 검색문서 여러 개)와 같은 방식. 근거 논문은 실재 확인됨.

재판정 — 최종 1개 선택

rerank() · gpt-5-mini · 후보 상위 20개

후보 20개를 놓고 LLM이 딱 하나 고른다. 판정 순서: 1) 역할 적합성 → 2) 제품/서비스 직접일치 → 3) 해설서 포함 예시 → 4) 해설서 <제외> 위반 → 5) KSIC → 6) 계층. 후보 목록 밖 코드는 생성 금지. LLM이 스스로 신뢰도(high/mid/low)도 매긴다.

OpenAI 유료LLM 1회 · 입력 ~1만 토큰
▼

신뢰도 산정 + 조립

compute_confidence()

LLM 자기판단에서 시작해 검색 신호가 나쁘면 한 단계 낮추기만 한다 (후보 4위 이하 / 한쪽 검색만 / 1·2위 유사도차 얇음 / 근거 얕으면 low 확정). 대표 업종 1개 + 부가 0~2개 + 각각 신뢰도·대안 후보를 반환.

로컬 · 무료

※ 활동 1개당 OpenAI 3회 호출(구조화는 공통 1회 + 활동별 임베딩 1회 + 재판정 1회). 응답 보통 8~20초. 워커/큐 처리 또는 타임아웃 30초+ 권장.

07지금 진행 중: 계층 rerank 실험

질문: "후보 pool recall이 97.5%인데도 최종 선택이 자꾸 틀린다. 후보에 이미 들어있는 계층정보(대·중·소·세분류명)를 soft 신호로 써서 재판정 선택 오류를 줄일 수 있는가?"

무엇을 바꾸나

위 3단계 build_candidate_pool() 한 곳에만 hierarchy_fit() 순위 가감을 추가한다. 플래그 USE_HIERARCHY_RERANK = False 가 마스터 스위치 — 기본값에서는 v3와 정렬 결과가 바이트 단위로 동일(검증 완료). hard filter 아님, 후보 제거 없음.

핵심 설계

hierarchy_fit()은 business_role을 입력으로 받지 않는다. role 오판이 최대 실패원인인데 그걸 또 끌어오면 틀린 판단만 증폭한다. 대신 canonical_activity · product_service · search_keywords 와 후보 계층명의 겹침만으로 독립 계산해서, 틀린 role 페널티를 되돌릴 수 있는 별도 투표로 쓴다.

09팀원이 꼭 알아야 할 것

  1. 정확도 67% = 3건 중 1건은 1순위가 틀림. "AI 제안 + 사용자 확인" 구조가 전제. 자동 확정 절대 금지.
  2. gold_v2는 순환적이다. 해설서에서 파생됐는데 해설서를 검색에도 넣었다. 실전 정확도는 ~60% 안팎으로 보수적으로 봐야 안전.
  3. LLM이 비결정적이다. gpt-5-mini는 같은 입력에 run마다 다른 답. 42건 셋에서 ±7%p 스윙. 개선 측정 시 여러 번 돌려 중앙값을 봐야 한다.
  4. 실사용자 정답 데이터가 0건. 진짜 정확도·신뢰도 경계는 서비스 로그(user_selected_code)가 쌓여야 확정된다.
  5. 호출마다 재로드. match_business_code()가 매번 CSV·Chroma·OpenAI 클라이언트를 새로 만든다. 트래픽 있으면 모듈 전역 캐시 리팩터 필요.
  6. 실행: pip install -r requirements.txt → .env에 OPENAI_API_KEY → python -c "from industry_matcher import health; print(health())" → chroma_doc_count 14627 나오면 정상.

10용어집

canonical_activity
1단계에서 LLM이 만드는, 분류표 어투로 정규화한 활동명. 예: "매장에서 커피를 판다" → "커피 전문점".
business_role
사업자가 "실제로 무엇을 해서 돈을 버는가"를 18종 중 하나로 확정한 값. 제조·가공 / 도매 / 소매 / 음식·주점 / 중개·플랫폼 등. 이 값의 오판이 최대 실패원인.
BASE 채널 / EXAMPLE 채널
검색문서 DB를 둘로 나눈 것. BASE = 공식 정보(업종명·계층·KSIC·정의), 상위 25개 반드시 유지. EXAMPLE = 해설서 예시·제외, 상위 12개를 '추가만'(BASE를 밀어내지 못함).
후보 pool
2단계 검색 결과를 합쳐 순위 매긴 코드 목록. 3단계에서 role(및 실험 시 계층) 신호로 순위 조정. 4단계 재판정은 이 pool의 상위 20개만 본다.
재판정 (rerank)
4단계. 후보 20개를 놓고 LLM이 최종 1개를 고르는 단계. 검색(후보 생성)과 분리된 검증 단계 — BEACON 방식.
confidence (high/mid/low)
재판정 LLM의 자기판단 + 검색 신호 가드(낮추기만). 학습된 확률 아님. UX 분기용.
gold_set_v1 / v2
v1 = 42건 손선별, 해설서 무관(비순환). v2 = 240건, 해설서 <예시>/<제외>를 LLM이 사업설명으로 풀어씀. 넓고 어렵지만 순환적.
pool recall
정답 코드가 후보 pool에 (전체 / 상위 20위 안에) 들어있는 비율. 검색 품질 지표. 현재 97.5%.
PSST
Problem–Solution–Scale–Team. 창업 사업계획 프레임. 이 기능은 그중 슬롯 0(아이디어)·2(문제)·5(솔루션)를 입력으로 쓴다.

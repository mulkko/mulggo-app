01

이 기능이 하는 일

물꼬는 소상공인·예비창업자가 자기 사업을 설명하면 그에 맞는 정부 지원사업·상권·지역 정보를 이어 주는 서비스입니다. 그 첫 단추가 업종 확정입니다. 사용자는 업종코드를 모르지만, 뒤쪽 모든 매칭(지원사업 자격, 상권 통계)은 코드가 있어야 돌아갑니다.

그래서 이 파트는 자연어 사업 설명 한 덩어리를 받아 업종코드-표준산업분류 연계표의 6자리 코드(총 1,612개) 중 하나로 매핑합니다. 예:

“직접 원두를 볶아 카페에서 팔고 일부는 도매로 납품합니다”  →  154901 커피 전문점(대표) + 552303 볶은 커피 제조(부가)

기존 ksic_core/, scripts/ 파이프라인은 건드리지 않습니다. 이 기능의 코드는 전부 business_matching/ 안, 파일명 21_~29_ 입니다.

02

어떻게 작동하나 — 3단계

입력 한 건이 아래 3단계를 거쳐 코드 하나(+대안 2·3순위)와 신뢰도 등급으로 나옵니다. 본체는 23_match_business_code_v3.py.

STEP 1

후보 검색 (retrieval)

LLM이 사업 설명을 “~업 / ~제조업” 같은 분류표 어투로 다듬고, 여러 표현으로 임베딩 검색 + 키워드 검색을 함께 돌려 후보 15~20개를 모읍니다. DB는 통계청 해설서 기반 business_code_docs_2025.

STEP 2

재판정 (rerank)

LLM이 후보 목록을 놓고 사업자 역할(제조/도매/소매/음식점 등)과 세세분류명을 대조해 딱 하나를 고르고 이유를 답니다. 역할이 상충하는 후보는 먼저 탈락.

STEP 3

신뢰도 산정

LLM 자기판단(high/mid/low)을 출발점으로, 검색 신호가 나쁘면 한 단계 낮춥니다(올리진 않음). 몇 위 후보를 골랐나 · 두 검색에 다 잡혔나 · 1·2위 유사도 차이가 신호입니다.

A / B / C 표기는 평가용입니다 — A: 원문을 그대로 임베딩 검색, B: A + LLM 다듬기·재판정 전 단계, C: 최종 결과(위 3단계 전부). 아래 성능 표에서 계속 나옵니다.

04

신뢰도 등급의 진짜 의미

결과마다 high / mid / low가 붙습니다. 29_calibrate_confidence.py로 240건에서 등급별 실측 정확도를 뽑았습니다(저장된 평가 결과만 분석, API 비용 0).

신뢰도 등급 — 데이터 기반 재설정 전 / 후 (2026-09-09)
등급비중(기존)실측 정확도(기존)비중(개선 후·시뮬)실측 정확도(개선 후)
high65%72.0%54%73.8%
mid34%30.5%30%42.3%
low0.4%—16%30.8%

개선 후 가드(compute_confidence())는 v2 실측에서 나온 갈림 지점을 그대로 반영합니다:

  • 재판정이 고른 후보 순위 — 1~3위 67% vs 4위+ 37%. 급락 지점이 4위라서, rank ≥ 4면 한 단계 하향(기존 임계값 6위는 너무 느슨했음).
  • 벡터·키워드 동시 검출 O 66% vs X 33%. 한쪽에서만 잡히면 순위와 무관하게 하향.
  • 1·2위 유사도 차 >0.15 → 71% vs ≤0.06 → 43%. margin < 0.06이고 1위도 아니면 하향.
  • 근거가 확실히 얕은 경우(6위+ & 한쪽 검색만)는 low로 확정.

핵심: 넓은 입력에서는 “확실한” 등급이 안 나온다

어떤 신호 조합으로도 정확도 80%를 못 넘습니다(가장 빡세게 걸러도 high & 1~3위 & 동시검출 & margin≥0.1 → 79%, 전체의 30%만 해당). 따라서 high는 “확실”이 아니라 “십중팔구”로 읽어야 하고, 자동 확정 금지 — 반드시 사람 확인(보정 UI) 단계가 필요합니다. v1 42건에서 나온 “high = 95%”는 쉬운 셋 과적합이었습니다.

근본 원인 1개

현재 검색 인덱스(business_code_docs)는 업종코드의 이름·계층·연계 KSIC·설명만 담고 있고, 통계청 해설서의 <예시> 활동 문구는 안 담았습니다. 그런데 우리는 그 예시를 이미 27_parse_ksic_haeseol.py로 5,411개 추출해 뒀습니다 (data/processed/ksic_haeseol_examples_v1.csv). 정답을 오직 예시 문구로만 찾을 수 있는 케이스가 많은데, 그게 검색 인덱스에 빠져 있습니다.

다음 할 일

1순위 — 해설서 예시를 검색 문서에 추가

각 업종코드에 “그 코드에 속하는 해설서 예시 활동들”을 문서로 붙여 벡터 DB를 다시 만듭니다. 검색 실패 47건 중 상당수를 직접 겨냥합니다. 작업 흐름: 25_ 문서 생성 스크립트에 예시 소스 추가 → 26_ 재색인 → 24_ 재평가.

주의 — 재평가 점수는 부풀려질 수 있음

gold_set_v2의 사업 설명은 해설서 예시를 LLM이 풀어 쓴 것이라, 예시를 그대로 색인하면 재평가 Top-1이 인위적으로 올라갑니다. 정직한 검증은 해설서에서 안 나온 별도 셋이 필요합니다. 다만 실제 제품에는 이게 옳은 방향입니다 — 해설서 예시가 곧 “이 활동은 이 코드”라는 공식 근거니까요.

그 다음 후보

  • “기타 / 그 외” 코드에 상위 계층·형제 코드 설명을 덧붙여 검색 가시성 올리기.
  • 재판정 실패 55건 중 정답이 20위권 밖이던 케이스 → 후보 pool 크기·다중쿼리 확대.
  • 불완전한 사업 아이디어를 사용자에게 되묻는 흐름(합의된 계획 5번).
  • 업종 확정 이후의 보정 UI / 로그(사람이 고친 기록 축적 → 나중에 재학습·임계값 근거).
